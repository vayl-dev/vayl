# v0.7.0 — Tenant isolation and correctness

_27 September 2026_

{% hint style="warning" %}
**Back up before upgrading.** Schema migration v2 is not additive: 0.6 refuses to start on an upgraded database, so rolling back means restoring the backup. With the graph enabled, run `vayl-migrate reproject-graph` once after upgrading.
{% endhint %}

## Security

* **Reconcile policies are isolated per tenant.** One tenant's `set_reconcile_policy` could replace another tenant's policy for the same `user_id`. Migration v2 rebuilds the policy table with the tenant in its key.
* **Graph edges are isolated per tenant.** The Neo4j namespace now starts with the tenant, so tenants sharing a `user_id` no longer share `recall_related` edges or erase each other's. Rebuilding one tenant's graph no longer wipes every tenant's.
* **Decisions, receipts and the audit log are tenant-scoped** (migration v3, additive). Lookups, listings, redaction and retention purges only see the caller's tenant.
* **Principal management stays inside a tenant.** An admin of one tenant could create a key in another tenant. Now only the **deployment operator** (an admin of the `default` tenant, including the local stdio admin) can act across tenants; other admins manage only their own. `stats`, seat usage and the deployment-wide audit purge are operator-only.

## Fixed

* A `COEXIST` on the same scope can no longer leave two active values for one fact.
* `forget` on an approval-gated slot reports the queued removal instead of "Nothing matching to retract".
* `remember` no longer lists skipped facts under "Stored:".
* `check_before_act` and `safe_recall` list each reason once; `pending_changes` shows removals as `REMOVE subject: 'value'`.
* A `delete` that erases nothing issues no receipt.
* The MCP `serverInfo.version` is Vayl's version.
* A bad `VAYL_LOG_LEVEL` or `VAYL_OIDC_ROLE_MAP` fails at startup, naming the variable.

## Added

* `vayl-migrate reproject-graph` rebuilds the graph for every tenant from the store.
* An OpenAPI spec for `vayl-server` (`openapi/vayl-server.yaml`), which drives the API Reference.

## Upgrading from 0.6

1. Back up the database (and, with `VAYL_KMS=file`, the key files).
2. Start 0.7.0, or run `vayl-migrate up`. Migrations v2 and v3 apply in one transaction.
3. With the graph enabled, run `vayl-migrate reproject-graph` once.
4. In a multi-tenant deployment, decisions, receipts and audit rows written before the upgrade are stamped `default`, so only the `default` tenant sees them.

Single-tenant and stdio deployments behave as before.
